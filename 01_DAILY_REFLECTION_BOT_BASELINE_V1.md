# Daily Reflection Bot
## Technical Specification v1.0

**Статус:** утверждённая спецификация первой версии  
**Формат продукта:** приватный Telegram-бот для двух пользователей  
**Основная задача:** ежедневная короткая фиксация субъективной оценки дня с накоплением истории, базовой статистикой и возможностью экспорта данных.

---

# 1. Цель продукта

Бот должен формировать устойчивую ежедневную привычку короткой рефлексии.

Каждый вечер бот самостоятельно инициирует опрос и задаёт пользователю три коротких вопроса:

1. Как в целом прошёл день?
2. Как пользователь эмоционально чувствовал себя большую часть дня?
3. Сколько у пользователя было энергии?

После этого пользователь может при желании оставить текстовый комментарий.

Все ответы сохраняются структурированно.

Пользователь должен иметь возможность:

- посмотреть запись за сегодняшний день;
- исправить её;
- посмотреть статистику;
- получить свои данные в CSV;
- настроить время ежедневного опроса;
- пропускать дни без негативных последствий.

Продукт должен поддерживать двух независимых пользователей одного Telegram-бота.

---

# 2. Основные продуктовые принципы

## 2.1. Минимальное трение

Обычный ежедневный сценарий должен занимать примерно 15–40 секунд.

Большинство действий выполняются через Telegram inline-кнопки.

Текст требуется вводить только при желании оставить рефлексию.

---

## 2.2. Рефлексия, а не диагностика

Бот:

- не ставит диагнозов;
- не интерпретирует психологическое состояние;
- не даёт психологических рекомендаций;
- не оценивает пользователя;
- не обозначает снижение показателей как проблему.

В v1 бот только собирает, хранит и агрегирует данные.

---

## 2.3. 3/5 — нормальный результат

Шкала оценки дня:

| Балл | Интерпретация |
|---|---|
| 1 | Очень плохо |
| 2 | Плохо |
| 3 | Нормально |
| 4 | Хорошо |
| 5 | Отлично |

3 является нормальным нейтральным днём, а не отрицательным результатом.

---

# 3. Пользователи

В первой версии поддерживаются только два заранее разрешённых Telegram-пользователя.

Например:

- User A;
- User B.

Авторизация выполняется по `telegram_user_id`.

Список разрешённых пользователей задаётся конфигурацией приложения или заносится в БД при первоначальной настройке.

Если неизвестный пользователь запускает бота, бот отвечает:

> Этот бот является приватным.

После этого никаких функций ему не предоставляет.

---

# 4. Приватность пользователей

Записи каждого человека являются отдельными.

По умолчанию пользователь:

- видит только собственную историю;
- видит только собственную статистику;
- экспортирует только собственные данные.

Текстовые рефлексии одного пользователя другому автоматически не показываются.

Совместная статистика пары не входит в v1.

Архитектура БД при этом должна позволять добавить такую функцию позднее.

---

# 5. Ежедневный сценарий

## Шаг 1. Инициирование опроса

В установленное пользователем время бот отправляет:

> 🌙 **Итоги дня**
>
> Как в целом прошёл твой день?

Inline-кнопки:

- 😞 1
- 🙁 2
- 😐 3
- 🙂 4
- 😄 5

После нажатия значение сохраняется временно в состоянии текущего опроса.

---

# 6. Вопрос 1 — Day Score

Текст:

> **Как в целом прошёл твой день?**

Значения:

| Value | Label |
|---:|---|
| 1 | very_bad |
| 2 | bad |
| 3 | neutral |
| 4 | good |
| 5 | excellent |

Поле БД:

`day_score`

---

# 7. Вопрос 2 — Mood Score

После ответа на вопрос 1 бот редактирует или отправляет следующее сообщение:

> **Как ты себя эмоционально чувствовал большую часть дня?**

Кнопки:

- 😞 1
- 🙁 2
- 😐 3
- 🙂 4
- 😄 5

Поле:

`mood_score`

---

# 8. Вопрос 3 — Energy Score

Текст:

> **Сколько у тебя сегодня было энергии?**

Кнопки:

- 🪫 1
- 🔋 2
- 🔋 3
- ⚡ 4
- ⚡ 5

Поле:

`energy_score`

---

# 9. Текстовая рефлексия

После третьего ответа:

> **Хочешь оставить пару слов о сегодняшнем дне?**

Кнопки:

- ✍️ Записать
- Пропустить

Если пользователь выбирает `Записать`:

> **Что сегодня сильнее всего повлияло на твою оценку дня?**
>
> Напиши в свободной форме.

Следующее текстовое сообщение пользователя сохраняется как:

`reflection_text`

Ограничение разумной длины, например 4 000 символов.

Если выбран `Пропустить`:

`reflection_text = NULL`

---

# 10. Завершение опроса

После окончания бот отвечает:

> ✅ **Готово**
>
> День: 🙂 **4/5**  
> Настроение: 😐 **3/5**  
> Энергия: 🔋 **3/5**
>
> Запись сохранена.

Если присутствует комментарий, повторять его в итоговом сообщении необязательно.

---

# 11. Одна запись в день

Для комбинации:

`user_id + local_date`

может существовать только одна ежедневная запись.

На уровне БД требуется уникальное ограничение.

Например:

```text
UNIQUE(user_id, entry_date)
```

Повторное прохождение опроса за тот же день не должно создавать вторую строку.

---

# 12. Просмотр сегодняшней записи

Команда:

`/today`

Пример ответа:

> 📅 **18 сентября 2026**
>
> День: 🙂 4/5  
> Настроение: 😐 3/5  
> Энергия: 🔋 3/5
>
> 💬 Много работы, но вечером отлично провели время дома.

Кнопка:

`✏️ Изменить`

Если записи сегодня нет:

> Сегодняшней записи пока нет.

Кнопка:

`📝 Заполнить сейчас`

---

# 13. Редактирование

При выборе `Изменить` пользователь снова проходит ежедневный опрос.

Старая запись не создаётся повторно.

Значения существующей записи обновляются.

Поле:

`updated_at`

изменяется.

В v1 хранить историю версий записи не требуется.

---

# 14. Ручное начало опроса

Команда:

`/checkin`

или кнопка главного меню:

`📝 Заполнить сегодня`

запускает ежедневный сценарий в любое время суток.

Если запись уже существует:

> Ты уже заполнял сегодняшний итог.

Кнопки:

- 👀 Посмотреть
- ✏️ Изменить

---

# 15. Напоминания

У каждого пользователя есть:

- время основного напоминания;
- время повторного напоминания;
- timezone.

Default можно задать конфигурацией.

Пример:

```text
checkin_time = 21:30
reminder_time = 23:00
timezone = Europe/Moscow
```

Время хранится отдельно для каждого пользователя.

---

# 16. Основное напоминание

В `checkin_time` приложение проверяет:

существует ли сегодняшняя запись пользователя.

Если нет — отправляет ежедневный опрос.

Если есть — ничего не отправляет.

---

# 17. Повторное напоминание

В `reminder_time` приложение снова проверяет наличие записи.

Если запись отсутствует:

> Кажется, сегодня мы ещё не подвели итог дня 🙂  
> Займёт меньше минуты.

Кнопка:

`📝 Заполнить`

Если запись уже существует — сообщение не отправляется.

---

# 18. Пропущенные дни

Пропуск дня является допустимым состоянием.

Система НЕ должна:

- автоматически создавать запись со значением 0;
- считать пропуск плохим днём;
- заставлять пользователя отвечать за вчера;
- неоднократно напоминать после второго уведомления.

В статистике отдельно может отображаться:

`Заполнено: 24 из 30 дней`.

---

# 19. Настройки

Команда:

`/settings`

Показывает:

> ⚙️ **Настройки**
>
> Ежедневный вопрос: 21:30  
> Повторное напоминание: 23:00  
> Часовой пояс: Europe/Moscow

Кнопки:

- 🕘 Изменить время
- 🔔 Изменить напоминание
- 🌍 Изменить часовой пояс

Для первой реализации допустим простой интерфейс без сложного timezone picker.

Можно предоставить несколько заранее определённых значений и возможность ручной настройки.

# 20. Статистика

Команда:

`/stats`

По умолчанию показывает последние 30 календарных дней.

Пример:

> 📊 **Последние 30 дней**
>
> Заполнено: **26 из 30**
>
> Средняя оценка дня: **3.8**
> Среднее настроение: **3.6**
> Средняя энергия: **3.4**
>
> 😄 Отличных: 5  
> 🙂 Хороших: 11  
> 😐 Нормальных: 7  
> 🙁 Плохих: 2  
> 😞 Очень плохих: 1
>
> Хороших и отличных дней: **62%**

Кнопки:

- 7 дней
- 30 дней
- 90 дней
- Год

---

# 21. Правила статистики

Средние показатели рассчитываются только по заполненным дням.

Пропущенные дни:

- не получают score;
- не входят в среднее;
- учитываются только в completion rate.

Например:

```text
completion_rate =
completed_days / days_in_period
```

Процент хороших дней:

```text
good_day_ratio =
count(day_score >= 4) / completed_days
```

---

# 22. Динамика

В v1 можно выводить простое сравнение:

> Последние 7 заполненных дней: **4.0**
>
> Предыдущие 7 заполненных дней: **3.5**

Не нужно делать интерпретации вроде:

> Ваше состояние значительно улучшилось.

Только фактические показатели.

# 25. Недельная рефлексия

Недельная рефлексия входит в v1 как дополнительная функция, но не должна мешать основному ежедневному сценарию.

Раз в неделю, например вечером воскресенья, после заполнения обычного check-in бот предлагает:

> 📖 Хочешь коротко подвести итог недели?

Кнопки:

- Да
- Не сейчас

Если пользователь выбирает `Да`, бот последовательно задаёт три текстовых вопроса.

### Question 1

> Что было лучшим событием этой недели?

### Question 2

> Что больше всего отнимало силы?

### Question 3

> Чего хотелось бы больше на следующей неделе?

Все вопросы добровольные.

Пользователь может нажать:

`Пропустить`

на любом этапе.

# 30. Состояния диалога

Ежедневный check-in должен использовать явную state machine.

Пример:

```text
IDLE
↓
WAITING_DAY_SCORE
↓
WAITING_MOOD_SCORE
↓
WAITING_ENERGY_SCORE
↓
ASK_REFLECTION
↓
WAITING_REFLECTION_TEXT
↓
COMPLETE
```

Недельная:

```text
WEEKLY_IDLE
↓
WAITING_BEST_EVENT
↓
WAITING_ENERGY_DRAINER
↓
WAITING_WANT_MORE
↓
COMPLETE
```

Необходимо корректно обрабатывать:

- неожиданный текст;
- повторное нажатие кнопки;
- рестарт приложения;
- `/cancel`, если будет реализован.

---

# 31. Требование к незавершённым сценариям

Не стоит хранить критически важное состояние только в памяти процесса.

Перезапуск приложения не должен повреждать уже сохранённые данные.

Допустим один из вариантов:

1. FSM storage в SQLite;
2. промежуточная запись draft в БД;
3. безопасный перезапуск текущего check-in с начала.

Для v1 вариант 3 допустим, если завершённые ответы никогда не теряются.

# 38. Scheduler

Планировщик отвечает за:

- ежедневные check-in;
- повторные напоминания;
- недельное предложение рефлексии.

Нельзя создавать отдельную вручную прописанную scheduler job для каждого календарного дня.

Расписание должно быть повторяющимся.

Scheduler должен учитывать timezone пользователя.

# 42. Логирование

Приложение должно логировать:

- запуск;
- остановку;
- scheduler events;
- ошибки Telegram API;
- ошибки БД.

Не логировать полный текст пользовательских рефлексий без необходимости.

---

# 43. Обработка ошибок

Пользователь не должен видеть traceback или внутренние исключения.

При ошибке:

> Что-то пошло не так. Попробуй ещё раз чуть позже.

Исключение полностью пишется в application log.

---

# 44. Работа после рестарта

После перезапуска приложения должны сохраняться:

- пользователи;
- настройки;
- ежедневные записи;
- недельные записи.

Scheduler должен автоматически восстановить свою работу.

---

# 45. Docker

Приложение должно запускаться:

```text
docker compose up -d
```

SQLite database должна храниться в persistent volume или bind mount.

Удаление контейнера не должно удалять историю.

# 47. Backup

Поскольку вся история пользователя ценна, необходимо обеспечить простой backup.

Минимально:

копирование файла:

```text
reflection.db
```

при остановленном приложении либо через корректный SQLite backup.

В README описать процедуру восстановления.

# 48. Тесты

Минимально покрыть автоматическими тестами:

### Database

- создание пользователя;
- уникальность Telegram ID;
- создание daily entry;
- невозможность двух записей на один день;
- обновление существующей записи.

### Statistics

- правильное среднее;
- пропуски не входят в среднее;
- правильный percentage хороших дней;
- правильный completion rate.

### Authorization

- разрешённый пользователь имеет доступ;
- посторонний пользователь не имеет доступа.

### Scheduler logic

- check-in не отправляется, если запись существует;
- reminder отправляется только при отсутствии записи.

# 49. UX requirements

Не использовать технические термины в сообщениях Telegram.

Плохо:

> DailyEntry successfully inserted.

Хорошо:

> ✅ Запись сохранена.

Сообщения должны быть:

- короткими;
- дружелюбными;
- нейтральными;
- без избыточной мотивационной риторики.

# 52. Критерии готовности v1

Проект считается готовым, если выполняется весь следующий сценарий.

### Пользователь A

1. открывает бота;
2. `/start` работает;
3. пользователь распознаётся как разрешённый;
4. в заданное время приходит вопрос;
5. можно выбрать day score;
6. mood score;
7. energy score;
8. оставить комментарий либо пропустить;
9. запись появляется в SQLite;
10. повторная запись этого дня не создаётся;
11. `/today` показывает данные;
12. данные можно изменить;
13. `/stats` корректно считает статистику;
14. `/export` присылает CSV.

### Пользователь B

Тот же сценарий работает независимо.

Записи пользователей не смешиваются.

### Scheduler

Если пользователь уже ответил:

повторное напоминание не приходит.

Если пользователь не ответил:

приходит одно повторное напоминание.

### Persistence

После:

```text
docker compose down
docker compose up -d
```

данные остаются на месте.

```text

export работает
```

Наличие написанного кода без работающего end-to-end сценария не считается завершением задачи.

# 54. Главный пользовательский сценарий v1

Итоговый продукт должен ощущаться так:

```text
21:30

Telegram:
Как прошёл твой день?

↓ одно нажатие

Как ты себя чувствовал?

↓ одно нажатие

Сколько было энергии?

↓ одно нажатие

Хочешь что-нибудь записать?

↓ текст или пропуск

✅ Готово
```

Основная задача первой версии — добиться того, чтобы этим хотелось пользоваться каждый день.

Все остальные возможности продукта вторичны.
